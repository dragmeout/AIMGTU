# Тезисы защиты лабораторной №2

**Цель:** превратить перечень предполагаемых источников из работы №1 в реальные, очищенные, воспроизводимые данные для RAG.

1. В реестре 14 официальных источников и кандидатов. Сохранено 7 оригиналов; 6 документов вошли в очищенную базу. Семь кандидатов возвращали внешний редирект, один PDF оказался сканом и не индексируется.
2. Сгенерированные проектные материалы не используются как факты о правилах университета. У каждого включённого текста есть URL, оригинальный снимок и SHA-256.
3. HTML очищается по содержательным контейнерам. PDF — по проверенной области страниц 3–16. Сохраняются пункты, списки, заголовки и страницы. Дата регламента 13.03.2024 прочитана с рукописного титула; текущая действующая редакция не подтверждена.
4. Два метода: фиксированные окна 180 слов с overlap 30 и смысловые блоки до 260 слов. В базе соответственно 35 и 34 chunks.
5. Один BM25 и 20 вопросов с точным evidence. Hit@3 — 85% и 90%; смысловой метод сохраняет 97/97 коротких блоков, контроль — 90/97. При этом контроль выигрывает Hit@1: 80% против 75% и MRR@5: 0,8475 против 0,8208.
6. Выбран смысловой вариант для RAG с несколькими найденными фрагментами. Выбор объясняется сохранностью правил и списков, меньшим повторением текста и top-3; это не доказательство общего превосходства embeddings или LLM.
7. Девять полей задания сохранены. Дополнительно — хеши, диапазоны страниц, актуальность, допустимое применение, разделы, версия алгоритма и временная метка загрузки. Неизвестная дата — `null`.
8. Обновление отделено от повторения эксперимента. Новый raw-хеш требует содержательного ревью и согласования `reviewed_raw_sha256`; ошибочные загрузки не заменяют источники чужими страницами.
9. Проверено полное покрытие текста и совпадение повторной сборки; 12 тестов прошли. Команда `all` работает офлайн на сохранённых исходниках.

**Демонстрация:**

```powershell
python scripts/prepare_data.py all
python scripts/search_kb.py "структура отчета по практике" --top-k 3
python -m unittest discover -s tests -v
```

Открыть `data/chunks/example.json`, `data/reports/chunking_comparison.md` и строку недоступного источника в `data/documents/manifest.json`.

**На вопрос «Почему база небольшая?»** — размер не подменяет проверяемость. Это реальный пилот с зафиксированными пробелами; недоступные стипендии и расписание группы не были выдуманы. Дальше нужно восстановить доступ, выполнить OCR и проверить действующие редакции.

**На вопрос «Почему именно смысловые chunks?»** — они лучше сохраняют целые положения. Но контроль лучше в top-1, поэтому при иной конфигурации retrieval выбор следует перепроверить.

**На вопрос «Это уже RAG?»** — подготовлен воспроизводимый вход для RAG. Векторная БД, embedding-модель и генератор будут следующими этапами.
