## 3. Допустимость использования данных

В рамках проекта установлен разрешённый состав: публичные официальные информационные страницы и опубликованные университетом нормативные материалы для локального учебного исследования с сохранением источника. Авторизация, обход ограничения доступа, сбор пользовательских форм и данных конкретных студентов не применяются.

Для каждого источника сохранены `permission_basis` и `license_status`. Публичная доступность не отмечается как открытая лицензия или письменное разрешение: таких подтверждений при сборе не обнаружено. Сборка предназначена для закрытого учебного использования; право на публичное переиздание полных исходных материалов не заявляется. Для публичного распространения корпуса команда должна отдельно определить разрешённый объём, лицензии или согласование правообладателей.

Реестр отражает проектное решение об отборе и техническую проверку ИИ; человеческое утверждение источников ещё не фиксировалось. Это прямо обозначено полем `review_status`, а не выдано за выполненное согласование с университетом.

## 4. Способ получения и воспроизводимость

Сбор выполнен программным GET по точным URL из реестра. Конвейер реализован в [`../scripts/prepare_data.py`](../scripts/prepare_data.py).

```text
sources.csv + preparation_config.json
    -> fetch: HTTPS, белый список, контроль редиректов и формата
    -> documents/raw/ + manifest.json + refresh_report.json
    -> build: проверка SHA-256 и допуска снимка, очистка, структурные блоки
    -> clean_documents.jsonl
    -> fixed.jsonl + semantic.jsonl -> final.jsonl
    -> compare + validate -> reports/
```

Официальный сайт Центра карьеры публикует `robots.txt`, запрещающий `/wp-admin/`; выбранные публичные страницы и файлы не относятся к этому пути. Конвейер не обходит сайт рекурсивно, не отправляет формы, не выполняет JavaScript и не обращается в личный кабинет. Ссылки на сторонние ресурсы сохраняются как текстовые ссылки, но не становятся автоматически разрешёнными источниками.

При загрузке проверяются:

1. HTTPS и точный hostname из белого списка; адрес вида `magtu.ru.example.com` не допускается.
2. Каждый редирект до запроса следующего адреса; переход к внешнему домену запрещён.
3. HTTP-результат, Content-Type и ожидаемый формат; PDF проверяется по сигнатуре `%PDF`.
4. Ограничение размера 12 МБ и тайм-аут 25 секунд.
5. Для HTML — наличие согласованного содержательного контейнера.

Оригинал записывается под именем `<document_id>_<16 символов SHA-256>.<format>`. Полный SHA-256, URL, конечный адрес, время загрузки с UTC+05:00, размер и серверный Last-Modified хранятся в `manifest.json`. Заголовок Last-Modified — технический признак изменения; он не подменяет дату утверждения или публикации.

Разделены два режима:

- **Повторение эксперимента:** команда `all`, без сети, на приложенных снимках. Фрагменты воспроизводятся побайтно; это проверено повторной сборкой.
- **Получение новых данных:** отдельная команда `fetch`. Новые страницы могут отличаться; это новая версия корпуса, которая требует проверки.

Зависимости зафиксированы в `requirements-data.txt`; фактические версии Python и пакетов записаны в `build_manifest.json`. В базе нет зависимости от API языковой модели, видеокарты, облачного сервиса или платной подписки.

## 5. Очистка документов

### 5.1. HTML

HTML декодируется строго как UTF-8. Извлекается согласованный контейнер (`#post-71`, `#post-67`, `#post-318`, `#post-20`, `.search-section`), а не весь видимый текст страницы. Это исключает основное меню, общую форму консультации, отзывы, footer и счётчики.

Удаляются JavaScript, CSS, формы, inputs, кнопки, iframe и noscript. Текст нормализуется в NFC; неразрывные пробелы заменяются обычными, мягкие переносы и невидимые технические символы удаляются. Заголовки сохраняются как `section_path`. Абзацы становятся структурными блоками; ссылки приводятся к абсолютным адресам. Списки сохраняют маркеры и порядок пунктов.

Подписи SIG и повторяющие название документа ссылки на detached signatures исключаются из извлечённого текста; оригинал сохраняет их. На странице «О нас» индексируется вводный раздел и общий номер, а блок команды и индивидуальные рабочие контакты сотрудников исключены. Пустые подписи к изображениям «За практику» и «За трудоустройство» не становятся отдельными знаниями.

Таблицы HTML конвертируются в Markdown с заголовками столбцов. Если `<th>` отсутствует, создаются нейтральные имена столбцов; первая строка данных не теряется. Сложные `rowspan`/`colspan` требуют отдельного преобразования и переводят документ на проверку. В выбранных содержательных HTML-блоках фактических таблиц нет; обработчик проверен тестом с таблицей услуг и адресов. Таблицы не выдумывались ради отчёта.

### 5.2. PDF

В регламенте ВО индексируются страницы 3–16. Титульный лист и содержание используются для проверки реквизитов и структуры; приложения с формами не индексируются, поскольку для текущего пилота выбран основной текст. Эта граница записана в `page_range`, а не скрыта за заявлением о полном извлечении PDF.

Повторяющийся табличный колонтитул исключается геометрически: из каждой страницы берётся область от 138 pt до `height − 35 pt`. Координаты согласованы с текущим PDF. Смена макета или появление таблицы внутри основной области требует пересмотра; новый PDF не должен автоматически обрабатываться старыми координатами.

Использован `pdfplumber` с `x_tolerance=2`. Первоначальная проверка другим извлекателем обнаружила ложные внутрисловные пробелы, например «результа ты» и «подгот овка». Геометрический извлекатель восстановил «результаты» и «подготовка» без ручного переписывания содержания. Символ списка из приватной области Unicode заменён дефисом. Орфографические и редакционные особенности исходного регламента не исправляются как будто это ошибки извлечения.

Строки основного текста объединяются в пункты `1.1.`, `2.1.` и т.д. Списки остаются внутри соответствующего пункта. Пункт, продолжающийся на следующей странице, объединяется и сохраняет несколько номеров страниц. Разделы и номер пункта входят в `section_path`. Перенос после лексического дефиса соединяется с продолжением слова с сохранением дефиса.

Обнаружена особенность титула: текстовый слой содержит пустые поля даты и номера, но поверх них находятся рукописные реквизиты. По изображению страницы 1 прочитаны **13.03.2024, протокол №6**. В метаданных это `date=2024-03-13`, `date_basis=approval_handwriting_visual_check_page_1_protocol_6`. Чтение изображения выполнено ИИ; команда должна сверить реквизиты при приёмке. Проверка наличия более новой редакции не выполнена, поэтому статус документа остаётся `approval_seen_current_validity_unconfirmed`.

В основной области выбранного PDF содержательных таблиц нет; видимая таблица — колонтитул. Если при следующей загрузке PDF будет обнаружена таблица в основном тексте, конвейер не превращает её в ненадёжный поток слов, а исключает документ до согласованного извлечения таблицы. Сканированный второй PDF также исключён до OCR.

### 5.3. Дубликаты и контроль потерь

Дедупликация документа выполняется по SHA-256 очищенного текста; при совпадении сохраняется документ с более высоким приоритетом источника и фиксируется canonical ID. Повторный абзац удаляется только при одинаковом тексте и одинаковом структурном пути. Одинаковые формулировки в разных нормативных пунктах сохраняются, поскольку имеют разный контекст.

В текущем корпусе полных дубликатов документов и одинаковых абзацев внутри одного раздела не обнаружено. Это реальный нулевой результат, а не незаполненный этап. Исключение общих меню, отзывов и SIG-ссылок выполняется структурно до дедупликации.

Каждый блок имеет диапазон символов в каноническом тексте. После chunking проверяется покрытие всех непробельных символов обоими вариантами: потери данных не обнаружены. У фрагментов сохраняются хеш текста и точный диапазон; это позволяет проверить, что содержание не было дописано моделью.

## 6. Два варианта chunking

Размеры измеряются в словах, разделённых пробельными символами. Это воспроизводимая единица без зависимости от токенизатора. Перед выбором embedding-модели дополнительно потребуется проверить лимиты её токенизатора; 260 слов не объявляются равными 260 токенам.

### Вариант A — фиксированные окна

- Размер: 180 слов; перекрытие: 30 слов; шаг: 150 слов.
- Окна строятся в пределах одного документа, без переноса текста между документами.
- Граница совпадает с границей слова, но может разрезать нормативный пункт, список или абзац.
- Последнее окно может быть меньше 180 слов. Маленькие HTML-документы остаются одним фрагментом.
- Разделы, ID блоков и страницы затронутых блоков сохраняются как метаданные.

Преимущества: простой алгоритм, предсказуемая длина, перекрытие сохраняет часть пограничного контекста. Недостатки: повторение текста, возможность разрезать условие и исключение либо начало и конец списка.

### Вариант B — смысловые блоки

- Основа: абзац/список HTML или целый нормативный пункт PDF.
- Соседние небольшие блоки объединяются внутри одного раздела; целевой размер 180 слов, максимум 260.
- В PDF соседние пункты одного раздела могут быть вместе, но сохраняют собственные структурные пути.
- Между разными разделами объединение не выполняется.
- Блок больше 260 слов делится окнами по 260 слов, перекрытие 30; фрагменты получают `fallback_split=true`.
- Все номера страниц блока сохраняются, в том числе при продолжении пункта через границу страницы.

Получено 34 фрагмента, из которых 4 — резервное разбиение двух длинных пунктов. Два длинных блока не помещаются целиком в один chunk; информация сохранена в нескольких chunks. Этот предел не скрывается утверждением, что смысловое разбиение никогда не разрезает текст.

## 7. Эксперимент и выбор метода

Сравнение выполнено на одинаковом очищенном корпусе и одном наборе вопросов. Реализация retrieval-контроля — BM25, `k1=1.5`, `b=0.75`; текст приводится к нижнему регистру, `ё` к `е`, исключаются короткие слова и небольшой фиксированный список служебных слов. Стемминг, embeddings, reranker и LLM не используются. Поиск выполняется по одинаковому виду представления: заголовок документа + текст фрагмента. При равенстве score применяется стабильная сортировка по chunk ID.

Для каждого из 20 ответимых вопросов заданы `document_id` и точные evidence-фразы из очищенного источника. Фрагмент считается полным подтверждением, если принадлежит нужному документу и содержит **все** необходимые evidence-фразы. Поэтому найденный общий документ ещё не означает успешный retrieval. Четыре сценария отказа сохранены для последующей оценки RAG; здесь процент корректных отказов не рассчитывается.

Вопросы включают процедуры согласования практики, договор, структуру отчёта, подписи, сроки по редакции 2024 года, доступные карьерные услуги и навигацию. Набор подготовлен ИИ и проверен программно на наличие evidence; человеческая разметка не заявляется. Это малый контрольный набор, а не 100-сценарный финальный benchmark из работы №1.

| Метрика | Фиксированные окна | Смысловые блоки |
|---|---:|---:|
| Число chunks | 35 | 34 |
| Медиана слов | 180 | 183 |
| Максимум слов | 180 | 260 |
| Символов во всех chunks | 47 258 | 40 754 |
| Объём chunks / очищенный корпус | 1,1725 | 1,0111 |
| Целые блоки ≤180 слов хотя бы в одном chunk | 90/97 (92,78%) | 97/97 (100%) |
| Целые блоки всех размеров | 90/102 | 100/102 |
| Hit@1 полного подтверждения | 16/20 (80%) | 15/20 (75%) |
| Hit@3 полного подтверждения | 17/20 (85%) | 18/20 (90%) |
| MRR@5 полного подтверждения | 0,8475 | 0,8208 |

Определения:

- **Hit@k:** доля вопросов, для которых в первых k результатах существует один полностью подтверждающий фрагмент.
- **MRR@5:** среднее `1/rank` первого полностью подтверждающего фрагмента; если его нет в первых пяти, вклад равен нулю.
- **Сохранность блока:** весь диапазон блока содержится хотя бы в одном chunk. Для честного сравнения основной показатель ограничен блоками ≤180 слов, которые по размеру помещаются в оба варианта.
- **Объём:** учитывается только `text`, без повторяемых метаданных и заголовка в `retrieval_text`.

Машиночитаемые результаты — `chunking_comparison.json`; ранги и score по каждому вопросу — `retrieval_details.jsonl`. Итоги пересоздаются командой `compare`, а не вписаны как желаемые проценты.

**Выбран вариант B, смысловые блоки.** Для RAG планируется использовать несколько найденных фрагментов. Поэтому полное подтверждение в top-3, сохранность нормативных пунктов и меньший объём повторяемого текста важнее выигрыша контроля в top-1. Выбор не означает превосходство по всем показателям: фиксированные окна дают лучшие Hit@1 и MRR@5, а разница Hit@3 составляет всего один вопрос. Если будущая система будет использовать только один результат, решение следует пересмотреть.

Общий объём текстовых payload при смысловом разбиении меньше на 6504 символа, то есть примерно на 13,8% относительно контроля. Это снижает повторение при дальнейшем индексировании. Списки вроде структуры отчёта п.6.4 сохраняются вместе с вводной формулировкой.

Ограничения эксперимента: небольшой корпус с преобладанием одного регламента; вопросы составлены по известным источникам; отсутствует проверка разговорных формулировок на семантической модели и генерации ответа. Нельзя переносить эти результаты на качество всех ответов или заявлять достигнутые faithfulness/hallucination metrics. После добавления источников и выбора embedding-модели оба варианта нужно сравнить повторно на расширенном, утверждённом командой наборе.

## 8. Metadata и формат хранения

Обязательная структура задания сохранена без переименования полей:

| Поле | Тип и значение |
|---|---|
| `document_id` | Стабильный ID документа, например `practice-guide` |
| `document_title` | Название источника, не выдуманное название ответа |
| `source` | Официальный URL оригинала |
| `date` | ISO-дата утверждения/публикации, `null`, если неизвестна |
| `document_type` | Локальный регламент, страница подразделения или навигация сервиса |
| `department` | Ответственное подразделение |
| `page` | Начальная физическая страница затронутого PDF-блока; `null` для HTML |
| `chunk_id` | `<document_id>:<12 знаков clean_sha256>:<method>:<порядковый номер>` |
| `text` | Точный фрагмент канонического очищенного текста |

Расширенные поля нужны для воспроизводимости и проверки ответа:

| Поле | Назначение |
|---|---|
| `pages`, `page_end`, `page_precision` | Все страницы затронутых блоков, конец диапазона и точность привязки |
| `section_paths`, `block_ids` | Связь с разделом, пунктом и исходными структурными блоками |
| `fetched_at`, `date_basis` | Время загрузки отдельно от даты документа; способ определения даты |
| `raw_sha256`, `clean_sha256`, `text_sha256` | Проверка оригинала, очищенной версии и фрагмента |
| `source_priority` | Приоритет доказательного источника |
| `validity_status`, `allowed_use`, `dynamic` | Ограничения актуальности и допустимого применения |
| `education_level` | Уровень образования; регламент ВО не применяется к СПО автоматически |
| `chunking_method`, `fallback_split`, `word_count` | Параметры и исключения алгоритма |
| `start_char`, `end_char` | Диапазон `[start_char, end_char)` в `clean_documents.jsonl` |
| `retrieval_text` | Заголовок документа + исходный фрагмент для индексирования |

Номер страницы соответствует физической странице PDF; в данном регламенте он совпадает с напечатанным номером листа. Привязка устанавливается на уровне целого исходного блока. Если chunk содержит лишь часть пункта с двух страниц, `pages` может включать обе: это консервативный диапазон для поиска в оригинале, а не точное положение каждого символа. Поле `page_precision=containing_block_page_span` явно отражает это ограничение.

Схема — `data/chunks/schema.json`, реальная запись — `data/chunks/example.json`. В ней сохранены все девять полей задания. JSONL выбран потому, что позволяет последовательно импортировать отдельные chunks в любой последующий индекс без привязки к конкретной векторной БД.

Один и тот же `document_id` переживает обновление источника, а ID фрагментов меняется вместе с хешем очищенного текста. Поэтому результаты старого ответа нельзя ошибочно связать с другим содержимым после обновления.

## 9. Правила обновления базы

### Периодичность

| Группа | Период проверки | Особенность |
|---|---|---|
| Навигация расписания | Ежедневно | Хранится адрес сервиса; занятия конкретных групп не копируются |
| Контакты и страницы услуг | Еженедельно | Изменения адресов/телефонов требуют проверки |
| Общие нормативные акты | Ежемесячно и при сообщении о новой редакции | Проверяются реквизиты, действие и замена документа |
| Размеры стипендий, если будут добавлены | Перед началом семестра и при новом приказе | Старые суммы не становятся актуальными по дате скачивания |
| Недоступные кандидаты | Еженедельно до восстановления доступа | Нельзя подменять недоступный первоисточник поисковым пересказом |

Периоды — регламент команды, автоматическое расписание в системе не создавалось. Конкретные значения для включённых источников указаны в `update_interval_days`.

### Процедура выпуска новой версии

1. Сохранить текущую версию проекта, включая raw, реестр, manifest и итоговые chunks; обновление выполнять в копии или отдельной ветке.
2. Выполнить `fetch`; проверить `refresh_report.json`: добавлено, изменено, без изменений, исключено из реестра, ошибка доступа.
3. Сопоставить новый оригинал со старым. Проверить официальность адреса, структуру, лицензионное основание, дату и реквизиты. При одинаковом raw-хеше повторное согласование не требуется.
4. Если raw-хеш изменился, конвейер не индексирует документ до совпадения с полем `reviewed_raw_sha256`. После содержательного ревью ответственный участник обновляет реестр, параметры извлечения, date/status и reviewed-хеш. Повторные HTML-формы могут менять сырой хеш без изменения знаний; это проверяется сравнением содержательного блока.
5. Скан, неверный формат, пропавший контейнер и сложная таблица помещаются вне индекса до исправления. Исправление текста записывается как правило извлечения, а не незадокументированная ручная правка JSONL.
6. Выполнить `all` и тесты. Проверить покрытие символов, метаданные, размеры, источники и результаты контрольного набора.
7. Для изменённых действующих документов пометить старую редакцию архивной; в будущий рабочий RAG-индекс включать утверждённую новую сборку целиком. Не смешивать chunks разных версий. Переключение индекса и rollback относятся к реализации следующего этапа.
8. Сохранить новый `build_manifest.json` и журнал принятого решения. Если проверка ухудшила retrieval, выяснить причину до выпуска.

При ошибке доступа старая копия физически сохраняется, но новое состояние получает `fetch_error`, а `last_good_snapshot` указывает на архив. Следующая сборка исключает такой источник; старый действующий RAG-индекс остаётся отдельной версией с прежней датой. Документ, удалённый из реестра, исключается из новой базы, а не остаётся скрытым источником ответа.

Распределение ответственности предлагается команде по операциям: куратор источников проверяет актуальность и допустимость; ответственный за извлечение — разметку и OCR; ответственный за эксперимент — evidence и сравнение; выпускающий — тесты и версию. Индивидуальные выполненные вклады участников не выдумывались и не вписывались задним числом.

## 10. Проблемы и принятые решения

| Проблема | Решение и ограничение |
|---|---|
| Несколько исходных URL перенаправляют на Google | Редирект блокируется, ошибка регистрируется; нет мнимых документов со стипендиями или структурой |
| Недатированные HTML | `date=null`; загрузка не используется как дата документа; сведения только как снимок/навигация |
| Рукописная дата поверх пустого текстового поля PDF | Визуально прочитаны дата и протокол; метод проверки сохранён; актуальная редакция отдельно не подтверждена |
| Ложные внутрисловные пробелы при извлечении PDF | Применён геометрический извлекатель; смысл правил не переписывается |
| Повторяющийся табличный колонтитул | Исключён проверенной геометрической областью; параметры привязаны к снимку |
| Один нормативный PDF представляет скан | Сохранён вне индекса; OCR не заменён выдуманным текстом |
| Общее меню, формы, отзывы и индивидуальные контакты | Ограничены содержательные контейнеры и область «О нас»; формы не отправлялись |
| Разные адреса на странице практики и других блоках сайта | В корпус входит контакт именно выбранного блока практики; он не объявляется единственным адресом всего центра; для текущего маршрута требуется проверка |
| Длинные пункты и списки | Резервные окна до 260 слов с перекрытием; исключения отмечены флагом |
| Преимущество контроля по Hit@1 и MRR | Зафиксировано; выбор смыслового метода обоснован top-3 и сохранностью, а не заявлением об общем превосходстве |
| Частичное покрытие сценариев работы №1 | Зафиксирован список отсутствующих тем; будущий ассистент должен отказываться при отсутствии источника |

## 11. Проверка и готовность к RAG

Проверены: реальные URL и разрешённые домены, SHA-256 оригиналов, совпадение chunk с диапазоном очищенного текста, уникальность ID, отсутствие пустых фрагментов и повреждённых Unicode-символов, лимит 260 слов, соответствие итогового файла выбранному варианту и полное покрытие исходного очищенного текста.

Пройдено 12 автоматических тестов: блокировка внешних редиректов и обхода пути, сохранение таблицы/списка/ссылки, исключение мусора и формы, сложные таблицы, покрытие окон, страницы и реквизиты PDF, исключение скана/недоступных источников, неизвестные даты, совпадение повторной сборки, контекст структуры отчёта и наличие evidence у всех ответимых вопросов. Команда запуска:

```powershell
python -m unittest discover -s tests -v
```

Тексты титула, определений и структуры отчёта PDF дополнительно просмотрены по изображениям. Это выборочная визуальная проверка, а не постраничная проверка человеком всего корпуса. Проверка `validate` реализует перечисленные инварианты; поставляемая JSON Schema служит контрактом для следующего импортёра и отдельно сторонним валидатором на этом этапе не исполнялась.

Готовый вход следующего этапа — **`data/chunks/final.jsonl`**. Он содержит реальные фрагменты с происхождением и структурой, воспроизводится из приложенных оригиналов и сопровождается отчётом об ограничениях.

При подключении RAG требуется:

- применять `allowed_use` и `validity_status` до формирования ответа, не отвечать по неизвестно действующей редакции как по текущему правилу;
- передавать модели текст источников как данные, сохраняя запрет выполнять инструкции внутри документов;
- хранить версию корпуса с индексом и журналом ответа;
- показывать URL и диапазон страниц, уточнять контекст программы/курса, отказываться при недостатке данных;
- после выбора embedding-модели повторить сравнение и расширить benchmark до требований работы №1.

На данном этапе создана **воспроизводимая база для построения RAG**. Работающая генерация ответов, векторная индексация и эксплуатационная проверка актуальности в результат этого этапа не включены.
