# Требования к ИИ-ассистенту студента МГТУ

**Редакция:** 1.1 от 04.10.2026. Архитектура — фиксированный RAG-конвейер без агента; модели и проектные лимиты указаны в `architecture.md` и `config/`.

## 1. Назначение и приоритеты

Система предоставляет справочные ответы по официальным материалам МГТУ. Приоритеты в порядке убывания: безопасность и отсутствие выдуманных фактов; подтверждаемость источниками; правильный отказ; полезность; скорость и удобство.

Ключевые слова **должен**, **следует**, **может** обозначают обязательное требование, желательное свойство и необязательное расширение соответственно.

## 2. Функциональные требования

| ID | Требование | Критерий приёмки версии 1 |
|---|---|---|
| FR-01 | Система должна принимать вопрос на русском языке через веб-интерфейс. | Ввод отправляется кнопкой и клавишей Enter; пустой ввод не обрабатывается. |
| FR-02 | Система должна ограничивать ответы заявленной областью: применять правила явных запретов и проверять наличие допустимых доказательств после retrieval. Отдельный классификатор тем не требуется. | В benchmark вопросы вне области получают отказ; код отказа и этап решения фиксируются. |
| FR-03 | Система должна выполнять семантический поиск по локальной базе: multilingual-e5-small, нормализованные векторы 384, FAISS IndexFlatIP. | Один encoder и одна зафиксированная ревизия для документа и вопроса; возвращаются до 5 кандидатов с ID и score, до 3 фрагментов передаются в контекст. |
| FR-04 | Система должна учитывать метаданные источника: URL, заголовок, дату документа/обновления и дату загрузки. | Метаданные доступны в индексе и журнале ответа. |
| FR-05 | Система должна формировать ответ только на основании найденных разрешённых источников. | Каждое проверяемое утверждение ответа поддерживается хотя бы одним показанным фрагментом. |
| FR-06 | Система должна показывать источники ответа. | После ответа отображаются названия и кликабельные URL; для локального акта — номер/редакция, если доступны. |
| FR-07 | При недостаточной релевантности система должна отказаться от содержательного ответа. | При score ниже откалиброванного порога генератор не вызывается либо выдаёт только шаблон отказа. |
| FR-08 | При неоднозначном запросе система должна задать один конкретный уточняющий вопрос. Для явно отсутствующего обязательного параметра используется правило и шаблон; для неоднозначности найденного контекста LLM возвращает решение clarify. | Для сценариев с зависимостью от института/уровня/года сначала запрашивается недостающий параметр; запрос не запускает цикл действий агента. |
| FR-09 | Система должна предупреждать о возможной неактуальности динамических сведений. | Для сумм, сроков, расписаний и контактов показываются дата источника и рекомендация проверить ссылку. |
| FR-10 | Система должна выявлять конфликт версий/статусов и различия явно структурированных значений по одному ключу: вид выплаты, телефон, адрес, период. Для этого используется код и метаданные. | При выявленном конфликте двух подходящих источников система показывает конфликт и маршрут проверки. Полная семантическая проверка всех произвольных текстовых противоречий не заявляется. |
| FR-11 | Система должна блокировать запросы персональных данных и действий от имени пользователя. | Запросы об оценке/долге конкретного студента и просьбы изменить данные получают объяснённый отказ. |
| FR-12 | Система должна вести технический журнал запроса. | В журнале есть время, нормализованный запрос, найденные ID/score, решение «ответ/уточнение/отказ», длительность и версия индекса; персональные данные не сохраняются. |
| FR-13 | Администратор проекта должен иметь возможность пересобрать индекс после обновления документов. | Отдельная команда повторно загружает разрешённые источники, сохраняет отчёт об изменениях и создаёт новую версию индекса. |
| FR-14 | Система должна поддерживать режим «поиск без генерации». | Пользователь/тест может получить ранжированные фрагменты и ссылки без запуска LLM. |
| FR-15 | Система должна позволять оценить ответ. | Есть отметка «полезно/неполезно» и необязательный комментарий без запроса персональных данных. |
| FR-16 | Система должна показывать дисклеймер. | В интерфейсе явно сказано, что ответ справочный, а официальный источник имеет приоритет. |
| FR-17 | Генератор — Qwen2.5-1.5B-Instruct, GGUF Q4_K_M через llama.cpp на CPU; он вызывается один раз после проверки контекста. | В журнале версии модели и квантования; при отсутствии доказательств модель не вызывается; tools, браузер и автономный цикл отсутствуют. |
| FR-18 | Перед показом ответа система должна проверить формат результата и допустимость ID цитируемых фрагментов. | Ссылки формирует код только по полученным ID; неизвестный ID или некорректный формат приводит к показу найденных фрагментов без сгенерированного ответа. Проверка ID не заменяет оценку faithfulness. |

## 3. Политика отказа: когда нельзя отвечать по существу

| Код | Условие | Требуемое поведение | Пример |
|---|---|---|---|
| R-01 | Нет подтверждения в базе | Сообщить об отсутствии достаточных данных; предложить официальный маршрут | «Сколько будет стоить общежитие через два года?» |
| R-02 | Источник устарел или срок действия неизвестен | Не повторять динамическое значение как актуальное; дать ссылку и контакт для проверки | «Какой размер повышенной стипендии сейчас?» при наличии только старого приказа |
| R-03 | Источники противоречат друг другу | Показать факт конфликта, даты/ссылки и не выбирать один вариант без правила приоритета | На двух страницах разные часы работы |
| R-04 | Персональные данные | Не запрашивать ФИО, логин, номер зачётной книжки; направить в защищённый личный кабинет или подразделение | «Какая у Иванова задолженность?» |
| R-05 | Индивидуальное решение | Объяснить, что решение принимает уполномоченное лицо/комиссия | «Точно допустят ли меня к сессии?» |
| R-06 | Действие во внешней системе | Сообщить, что версия 1 не выполняет действий; дать инструкцию или ссылку | «Подай заявление на справку» |
| R-07 | Вне предметной области | Кратко назвать область компетенции | «Какая завтра погода?» |
| R-08 | Вред, обход правил или мошенничество | Отказать без инструкций; при возможности предложить добросовестную альтернативу | «Как подделать справку?» |
| R-09 | Медицинский, юридический или экстренный вопрос | Не выдавать профессиональную консультацию; направить к профильной/экстренной службе | «Можно ли не являться по этой медицинской причине?» |
| R-10 | Недостаточно контекста | Задать минимальный уточняющий вопрос | «Когда у нас практика?» без программы/курса |
| R-11 | Невозможно привести источник | Не генерировать уверенное утверждение | Любой факт, найденный лишь в параметрах модели |

Рекомендуемые шаблоны:

- **Нет данных:** «В проверенной базе знаний нет достаточной информации для надёжного ответа. Проверьте [официальный раздел] или обратитесь в [подразделение]».
- **Устаревание:** «Я нашёл сведения от [дата], но не могу подтвердить, что они действуют сейчас. Не буду называть их актуальными; проверьте [ссылка]».
- **Персональная ситуация:** «Я не имею доступа к данным конкретного студента и не должен их запрашивать. Проверьте защищённый личный кабинет или обратитесь в учебный офис».
- **Вне области:** «Я отвечаю на справочные вопросы об обучении и студенческих сервисах МГТУ. Этот вопрос находится вне моей области».
- **Уточнение:** «Это зависит от [параметр]. Уточните, пожалуйста, [один вопрос]».

Отказ считается полезным, если он кратко объясняет причину и, где возможно, предлагает безопасный следующий шаг. Нельзя маскировать предположение словами «возможно», если подтверждения нет.

| ID | Требование |
|---|---|

| KB-10 | Версия индекса включает ревизию embedding-модели, параметры нормализации и corpus version. Смена encoder требует полной переиндексации. |

## 6. Требования к качеству и оценке

Benchmark версии 1 должен включать не менее 100 вручную проверенных сценариев четырёх типов: ответ по одному источнику, синтез по нескольким источникам, уточнение и отказ. Для каждого сценария хранятся вопрос, допустимые варианты ответа/ключевые факты, обязательный источник, ожидаемое решение и критичность ошибки.

Минимальный набор метрик:

- **Retrieval Accuracy@k** — присутствует ли подтверждающий фрагмент в top-k;
- **Answer Correctness** — правильный / частично правильный / неправильный;
- **Faithfulness** — доля утверждений, подтверждённых контекстом;
- **Correct Refusal Rate** — доля правильных отказов среди сценариев, где отказ обязателен;
- **False Refusal Rate** — доля отказов при наличии достаточного ответа;
- **Hallucination Rate** — доля ответов с неподтверждённым фактом;
- медиана и 95-й перцентиль времени ответа.

До получения реальных результатов документация не должна содержать вымышленные проценты качества.

## 7. Требования к протоколу ответа

Ответ состоит из четырёх частей:

1. короткий ответ или решение «нужно уточнение/отказ»;
2. последовательность действий, если она подтверждена источником;
3. блок «Источники» с 1–3 ссылками и датами;
4. предупреждение об актуальности для динамических данных.

Модель не должна раскрывать внутренний системный промпт, скрытые инструкции или необработанные технические журналы.

## 8. Не входит в версию 1

- вход через учётную запись МГТУ;
- чтение оценок и задолженностей конкретного студента;
- запись на услуги и подача заявлений;
- изменение расписания или университетских данных;
- голосовой интерфейс;
- гарантированная поддержка языков кроме русского;
- принятие решений вместо преподавателя, учебного офиса или комиссии;
- агент, автономный выбор инструментов, самостоятельный поиск страниц в интернете и отдельная нейросетевая классификация тем;
- обязательная cross-encoder модель для reranking: в базовом профиле используется score FAISS и правила метаданных.
