# Основные пользовательские сценарии

**Редакция:** 1.1 от 04.10.2026.

## Общие участники и механизм

**Основной актор:** студент МГТУ. **Вспомогательный актор:** администратор базы знаний.

**Предусловия:** интерфейс запущен, локальная база и FAISS-индекс загружены; ревизии моделей, версия корпуса и дата проверки источников известны. Данные сайта заранее собраны администратором. Во время вопроса сайт не обходится, личный кабинет не открывается.

Сценарии выполняются одним фиксированным конвейером, показанным в `architecture_v2.png`:

- **UI** — получает вопрос и показывает результат;
- **G1** — программные правила явных запретов и обязательного уточнения;
- **E** — `intfloat/multilingual-e5-small` кодирует весь вопрос с префиксом `query: `;
- **R** — FAISS возвращает до 5 кандидатов из локального индекса;
- **G2** — код проверяет score, дату, допустимое применение и структурированные конфликты, выбирает до 3 фрагментов;
- **L** — `Qwen2.5-1.5B-Instruct`, GGUF Q4_K_M, один вызов для ответа или уточнения по контексту;
- **G3** — код проверяет формат/ID цитат, формирует URL из метаданных, показывает ответ или безопасный результат.

Отдельного шага нейросетевой классификации темы и агента нет. Метаданные `department`, `source`, `document_type`, `date` заполняются при подготовке базы. Ассистент не «выбирает и посещает подразделение»: он находит текст про подразделение в локальном индексе.

**Общее постусловие:** пользователь видит ответ, уточнение или отказ; для ответа — ссылки и даты. В технический журнал записываются ID/score, решение, версия индекса и длительность без персональных данных.

## UC-01. Найти официальный сервис или страницу

**Цель:** получить ссылку на расписание, календарь или официальный сервис.  
**Пример:** «Где посмотреть расписание экзаменов?»

**Основной поток:**

1. UI получает вопрос; G1 проверяет явные запреты.
2. E кодирует весь вопрос; R находит заранее индексированные описания сервиса или инструкцию.
3. G2 проверяет допустимость найденной навигационной записи и дату проверки ссылки.
4. L объясняет назначение сервиса и известные из контекста условия доступа.
5. G3 показывает URL из метаданных. Текст расписания конкретной группы не генерируется из общих сведений о сервисе.

**Альтернативы:** если нужна авторизация, показывается маршрут без запроса логина/пароля; при отсутствии навигационного источника — R-01. Недатированная страница может подтверждать адрес сервиса, но не текущие даты экзаменов.

**Результат:** проверяемая точка входа.

## UC-02. Получить инструкцию по справке или документу

**Цель:** понять процедуру и ответственное подразделение.  
**Пример:** «Как получить справку об обучении?»

**Основной поток:**

1. После G1 полный вопрос поступает в E и R; отдельное извлечение вида справки до поиска не выполняется.
2. R возвращает фрагменты инструкций, G2 проверяет действие и принадлежность нужной процедуре по метаданным.
3. При достаточном контексте L составляет шаги из найденной инструкции: куда обратиться, что подготовить, где получить результат.
4. G3 проверяет ID источников и показывает только подтверждённые сведения о сроках и документах.

**Альтернативы:** если найденные инструкции относятся к разным справкам, L возвращает один вопрос для уточнения; следующий вопрос пользователя заново проходит тот же конвейер. Отсутствие актуальной инструкции — отказ R-01/R-02. Просьба заказать справку — G1/R-06.

**Результат:** инструкция по источнику, без дополнительных требований от модели.

## UC-03. Узнать общие правила задолженности или пересдачи

**Цель:** получить общий порядок без решения личной ситуации.  
**Пример:** «Что делать, если я не сдал экзамен?»

**Основной поток:**

1. G1 проверяет, не запрашиваются ли личная оценка или решение о допуске.
2. E кодирует разговорную формулировку; R находит связанные с ней нормативные фрагменты без отдельной классификации «академическая задолженность».
3. G2 оставляет допустимые редакции и проверяет релевантность.
4. L излагает общий порядок и контакт, если он содержится в найденном контексте.
5. G3 показывает документ, редакцию/дату и URL.

**Альтернативы:** для даты личной пересдачи нужны опубликованные данные конкретной группы; общая норма не заменяет расписание. Индивидуальный допуск — R-05; отсутствие действующего акта — R-01/R-02.

**Результат:** подтверждённый общий порядок.

## UC-04. Узнать сведения о стипендии или материальной поддержке

**Цель:** получить подтверждённые общие условия и опубликованный размер выплаты.  
**Пример:** «Какой сейчас размер повышенной стипендии?»

**Основной поток:**

1. E и R находят документы по всему вопросу. Если вид выплаты не определён и найдено несколько процедур, формируется уточнение.
2. G2 проверяет период действия, вид выплаты и статус найденных источников. При сопоставимых действующих редакциях учитывается приоритет первичного приказа.
3. Для структурированных данных G2 сравнивает значения по ключу «вид выплаты + период»; выявленный конфликт ведёт к R-03.
4. Только при подтверждённой актуальности L формирует краткий ответ по контексту.
5. G3 показывает дату, документ и предупреждение, что назначение конкретному студенту определяется официальным решением.

**Альтернативы:** неизвестное действие/старая редакция — R-02; персональная выплата — R-04/R-05. Неструктурированные текстовые противоречия остаются риском, а не заявляются полностью решёнными обычными правилами.

**Результат:** сумма и условия не выдаются как текущие без подтверждения.

## UC-05. Разобраться с организацией практики

**Цель:** получить общий маршрут согласования места и оформления документов.  
**Пример:** «Можно ли пройти практику в выбранной мной компании?»

**Основной поток:**

1. E и R находят заранее индексированную страницу практики и фрагменты регламента.
2. G2 проверяет редакцию, уровень образования и допустимое применение источников.
3. L составляет последовательность действий по найденным пунктам, без обещания согласования компании.
4. G3 показывает найденные документы, общие контакты и ссылки на формы из метаданных/текста источника.

**Альтернативы:** если обязательный параметр программы/уровня отсутствует, задаётся один уточняющий вопрос. Если текущая редакция не подтверждена, она не выдаётся за действующую; для вопроса именно об историческом документе явно называется его дата.

**Результат:** справочный маршрут, а решение принимает ответственное подразделение.

## UC-06. Найти подразделение, контакт или адрес

**Цель:** определить, куда обратиться по вопросу.  
**Пример:** «Кто отвечает за организацию учебного процесса и где он находится?»

**Основной поток:**

1. UI передаёт полный вопрос через G1 в E. Отдельной предварительной классификации темы нет.
2. R ищет семантически близкие фрагменты заранее подготовленного справочника/страниц подразделений в FAISS.
3. G2 проверяет релевантность и актуальность контактов. Название подразделения, URL, адрес и телефон берутся из найденного документа и его метаданных.
4. L кратко объясняет подтверждённую компетенцию подразделения. Если подходят несколько, сопоставляет только найденные описания или задаёт уточнение.
5. G3 показывает контакт и официальный URL, сформированный кодом по source; LLM не создаёт адрес сайта самостоятельно.

**Альтернативы:** если актуальность контакта неизвестна, конкретный телефон/адрес не объявляется действующим; можно показать допустимую навигационную ссылку с датой проверки. Выявленный конфликт — R-03; источник отсутствует — R-01. Непубличные личные контакты не предоставляются.

**Результат:** найденное официальное подразделение из локальной базы. Агент, браузер и обращения в университетские системы для этого сценария не используются.

## UC-07. Обработать неподдерживаемый, личный или недостоверный запрос

**Цель:** корректно отказаться или уточнить вместо неподтверждённого ответа.  
**Примеры:** личные оценки, просьба изменить данные, вопрос вне темы, отсутствие актуального календаря.

**Основной поток:**

1. Для явных запрещённых шаблонов G1 сразу возвращает шаблон отказа; E/R/L не вызываются.
2. Если запрет не выявлен, E/R выполняют retrieval, а G2 проверяет достаточность и допустимость контекста.
3. При недостатке доказательств G2 выдаёт отказ до генерации. При известном недостающем параметре — шаблон уточнения.
4. При неоднозначности достаточного найденного контекста L может вернуть решение clarify вместо ответа; G3 проверяет формат.
5. UI показывает причину и допустимый официальный маршрут. Личные данные не запрашиваются и не сохраняются.

**Альтернативы:** после уточнения начинается новый проход конвейера. Если модель недоступна или вернула неизвестный ID источника, G3 показывает найденные фрагменты со ссылками либо техническое сообщение. Система не имитирует ответ.

**Результат:** отказ/уточнение проверяется отдельно; шаблонные правила не считаются гарантией распознавания всех перефразировок.

## Матрица связи с архитектурой

| Сценарий | Компоненты | Основной источник | Особая проверка |
|---|---|---|---|
| UC-01 | UI → G1 → E → R → G2 → L → G3 | Навигационная страница сервиса | Не выдавать расписание из описания сервиса |
| UC-02 | Тот же конвейер | Инструкция и метаданные процедуры | Уточнение вида справки по найденному контексту |
| UC-03 | Тот же конвейер | Действующий локальный акт | Не принимать решение о личном допуске |
| UC-04 | Тот же конвейер | Приказ, структурированные значения | Период действия, тип выплаты, конфликт значений |
| UC-05 | Тот же конвейер | Страница практики и регламент | Уровень образования, редакция |
| UC-06 | Тот же конвейер | Индексированные описания подразделений | Контакты и URL из источника, без агента |
| UC-07 | G1 → шаблон; либо E → R → G2 → шаблон; либо L → G3 → уточнение | Правила и найденный контекст | Генератор не вызывается при отсутствии доказательств |

Это ожидаемые сценарии будущего прототипа. Выполнение каждого сценария зависит от наличия соответствующего проверенного документа в базе; проектная схема не означает, что все данные уже собраны.
